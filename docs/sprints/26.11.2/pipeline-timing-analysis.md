## 一、结论摘要

1. **延迟 100% 发生在"运行对象被创建之前"，与我们的代码无关。**
   667 条运行的排队延迟（`run_started_at − created_at`）**全部为 0.0 分钟**（中位/p90/max 均为 0.0）；执行时长中位 **2.1 分钟**、p90 2.9 分钟。调度延迟中位 **282.7 分钟**、p90 421.4、max 740.8。也就是说：运行一出现就已经在跑，全部迟到发生在 GitHub 决定"创建这次运行"之前——这一段我们的仓库里没有任何代码能影响。

2. **六个档位全部实质失效。**
   全期只有 **7 次**（7/667 = **1.0%**）落在设计时刻 ±30 分钟内，且**全部**是 2026-08-17~08-26 的 13:35 档（22~31 分钟）。09:35 档 0/112、10:35 0/111、11:35 0/111、14:35 0/111、15:05 0/111。各档实际落点（中位 CST）：09:35 → **14:22**、10:35 → 15:20、11:35 → 16:21、13:35 → 17:56、14:35 → 19:12、15:05 → **19:24**。全天 194/667（29.1%）在 15:00 收盘前启动，12:00 前只有 30 次（4.5%）。

3. **延迟是"整日批量平移"，不是某一档掉队。**
   同一月份内六档的中位延迟相差 ≤50 分钟（如 11 月：410/432/472/458/492/486），说明不是某个 cron 被单独丢弃，而是整天的调度被整体推后。月度中位：6 月 260 → 7 月 182 → 8 月 83 → 9 月 308 → 10 月 366 → 11 月 464 分钟。8 月的"改善"只存在于 08-07~08-26，08-27 起跳变到 661/724 分钟，此后未恢复。

4. **唯一与我们自身相关的成本是 `checkout`，量级可忽略。**
   分步耗时显示 `actions/checkout@v4`：06 月 1~2s → 07 月 19s → 08 月 30~31s → 09 月 39s → 10 月 72s → 11 月 78~101s（随 archive 从 16 个目录长到 107 个、仓库 `size=177553KB`）。这解释了执行时长中位 1.38 → 2.82 分钟的上升，但对 282.7 分钟的调度延迟贡献 **<1%**。`pearson(exec, archive 目录数)=0.390`、`pearson(exec, 日序)=0.392`，弱正相关。提交频率恒定 6 次/工作日（112 个运行日中 111 天恰好 6 次），不是恶化原因。

5. **结论：GitHub `schedule` 不可能保证 09:35 这类盘中时点。**
   全期最早的一次落地是 08-18 13:57（run `32104875319`，延迟 22.0 分钟）——即使调度器"状态最好"的那 10 天，也没有一次做到盘中准点。若产品需要盘中数据，必须更换触发方式（外部定时器 `workflow_dispatch`）；但本仓库历史上 **0 次** `workflow_dispatch` 运行（667 条全部 `event=schedule`），dispatch 到运行的创建延迟**无法用现有数据确认**，需实测。

## 四、根因判定：外部不可控 vs 可以改

### a) 我们的 workflow 执行慢 —— **排除（证据：执行时长分布）**
执行中位 2.1 分钟、p90 2.9 分钟；即使把我们的作业压缩到 0 秒，数据落地时间也只提前约 2~3 分钟，相对 282.7 分钟的延迟改善 **<1%**。执行时长按月从 1.38 涨到 2.82 分钟，是 `checkout` 变慢，不是 build 变慢。

### b) 运行排队等 runner —— **排除（证据：排队延迟恒为 0）**
667/667 条 `run_started_at − created_at = 0.0 分钟`（精确到 0.0）。运行一旦创建即被分配 runner。公开仓库使用标准 runner 不计费额度，即使存在配额问题也会表现为排队，而观测到的排队为 0。

### c) workflow 被停用或降级 —— **排除（证据：workflow state）**
`GET /actions/workflows/market-data.yml` 返回 `state="active"`、`created_at = updated_at = 2026-06-04T15:18:55Z`（定义后从未被禁用或改写）。未出现 `disabled_*` 状态。

### d) 六档互相挤压 / 并发撞车 —— **基本排除（证据：重叠对与失败类型）**
- 执行时段重叠只有 **7 对**，且每一对都包含一次 6 小时超时的运行（例如 `28425428433` 14:39–20:40 与 `28426786141` 15:08–15:11）。正常运行 2~3 分钟，相邻运行创建间隔远大于执行时长，不存在"后一档把前一档挤掉"。
- 667 次里 659 success + 8 cancelled，**没有一次因 push 被拒而失败**（`stefanzweifel/git-auto-commit-action` 推送失败会让步骤失败、运行标红）。`concurrency` 是 11-09 才加入的，加入后 11-09 的运行排队延迟仍为 0，未引入等待。

### e) 6 小时超时的 8 次运行 —— **单独定性：数据源挂起，非调度问题**
`28425428433`、`29812282801`、`29818289078`、`30788643401`、`31159337849`、`31470281449`、`32441045732`、`36699483602`。
证据（`29812282801` 分步）：`Build market data` 07:56:17 → 13:55:57 `cancelled`，其余步骤正常；作业总时长 360.3~360.6 分钟 = GitHub 默认 360 分钟 job 超时。分布：6 月 1 次、7 月 2 次、8 月 4 次、9 月 1 次、10~11 月 0 次。这 8 次共消耗约 48 小时 runner 时间，但不改变时点结论（这些档位本来也不会准点）。

### f) 账户配额 / 仓库活跃度 —— **不适用（证据：无排队 + 公开仓库）**
公开仓库的 `schedule` 使用 GitHub 托管标准 runner，不计入付费分钟；且排队延迟恒为 0。账户级账单/配额信息需要认证后的 `/user`、`/settings/billing` 接口，匿名 API 不可读，**账户侧无法给出证据**；但"零排队"已足以排除该路径。

### g) 结论：延迟在 GitHub 调度器侧 —— **无法进一步定位**
可以确认的是：延迟全部发生在运行对象创建之前（排队=0、执行≈2 分钟）。`created_at` 本身可能已经是 GitHub 内部调度队列的出队时刻，因此**无法区分"cron 到点很晚才触发"与"触发了但在内部队列里压了很久"**。这一段既不在仓库代码里，也无法从 runs API 观测，属于外部不可控。

## 五、必须解释的三个异常

### 1. 8 月窗口（08-17~08-26，13:35 档 22~27 分钟）

**事实**：
- 08-07~08-26 的每日中位延迟 43~96 分钟（此前 07 月 ~150-210，此后 09 月 ~285-330）。
- 08-17~08-26 的 13:35 档落在 13:57 / 13:58 / 13:58 / 13:59 / 14:00 / 14:02 / 14:02（7 次全部 ≤30 分钟）；15:05 档落在 15:37~15:38（33~38 分钟，差一点也没进 ±30）。
- 08-27 突变为 661 分钟，08-28 为 724 分钟，08-31 回落到 382 分钟，9 月起稳定在 285~330。

**同期仓库侧有无变化**（逐条核过）：
- workflow 文件全历史只有 5 次提交：`1852097`(06-04)、`8a54c05`(06-09)、`69dca3d`(09-08)、`1676ad9`(11-04)、`3c83110`(11-09)。**8 月没有任何 workflow 改动**，更没有任何 cron 改动。
- 提交频率恒定：112 个运行日中 111 天恰好 6 次数据提交，8 月与 6/9/10 月一致。
- archive 目录数从 8 月初的 61 个平稳增长到月底的 83 个，`checkout` 当时为 30s 左右，执行时长中位 2.05 分钟，与 9 月（2.25）无显著差异。
- 运行结论：8 月 4 次 6 小时超时（本报告最多），但这些运行不影响其它档位的启动时刻。

**判定**：**无法从现有数据解释**。仓库侧不存在能解释"08-27 突然从 45 分钟跳到 661 分钟"的变化；这与 GitHub 调度器自身的负载/队列状态一致，但本报告没有 GitHub 状态页历史事件、也没有账户侧运行队列数据，**无法证实具体原因，不做因果归因**。可以确定的只有：这不是我们某次提交造成的（同期无提交）。

### 2. 月度恶化（6 月 260 → 8 月 83 → 11 月 464）

分三块看：
- **与执行时长相关？** 弱相关。执行中位 1.38 → 2.82 分钟（+1.44 分钟），`pearson(exec, 日序)=0.392`；但调度延迟增长 204 分钟（260→464），两者量级差两个数量级。
- **与提交频率相关？** 不相关。恒定 6 次/工作日，全期无变化。
- **与仓库体积相关？** 只影响 `checkout`。`pearson(exec, archive 目录数)=0.390`，checkout 从 2s 涨到 78~101s（+~1.5 分钟），build 本身没有变慢（06 月 41~43s vs 11 月 37~45s）。**这是唯一与我们自身相关的一条，已量化：对总延迟贡献 <1%。**
- **真正的拐点**是 08-27 的跳变，以及 9 月后 308→366→464 的单调抬升；两段都没有对应的仓库变化。**判定为调度器侧，无法进一步归因。**

| 2 | 删掉 `09:35 / 10:35 / 11:35` 三档，只留 `13:35 / 15:05` | 运行次数减半（约 333 次/期），时点不变 | 极低 | 上午彻底无更新（现状本来也没有：12:00 前仅 30/667） | 否 |
| 3 | 外部定时器（Cloudflare Cron → `workflow_dispatch`） | 把"创建延迟"从 ~280 分钟压到秒级~分钟级（**理论值，本仓库无 dispatch 样本**） | 中：PAT + Worker + 告警 | PAT 权限过大/泄露；Worker 单点；需实测 dispatch 到运行的延迟与 6 档并发 | **可能**，但 dispatch 触发延迟**无法用现有数据确认**，且 build 仍需 2~3 分钟 |
| 4 | 提前量"骗"延迟（把 cron 改到 04:35 等） | 不可行 | 低 | 延迟离散度 22~741 分钟，任何固定提前量都会在部分日子落到盘中或前一日；还会增加非交易日无效运行 | 否 |
| 5 | 自建 runner / 加大 runner | 无效 | 高 | 问题在运行创建之前，换 runner 不改变创建时刻 | 否 |
| 6 | 缩小仓库体积（浅克隆、拆分 archive、checkout 只取所需） | 省 60~100s；时点不变 | 中 | 改动数据目录结构，影响前端与回测读取 | 否（但对成本/稳定性有益） |
| 7 | 盘中改用轻量数据源（只拉指数/榜单，不做全量 rebuild） | 盘中可用；全量仍走收盘后 | 中高 | 新数据源口径/限流；与现有前复权口径需对齐 | **可能**，且比 3 更现实 |
| 8 | 非交易日跳过（交易日历 guard） | 省 42 次运行/期，消除假快照 | 低 | 需可靠交易日历；日历不可用时退化为工作日（已知误报点） | 否 |

**诚实结论**：GitHub 托管 `schedule` 在本仓库 5 个月、667 次样本上**没有一次**做到盘中准点（最早 22 分钟，中位 282 分钟）。任何"继续用 cron、只改提前量或改代码"的方案都无法达成 09:35。要盘中时点，只能换触发通道（选项 3 + 7），且必须先用 1~2 周实测 dispatch 的真实延迟，不能按理论值承诺。

## 八、建议方案

### 立即（不改产品口径）
1. **保持已落地的 `concurrency` + 提交重试 + 新鲜度自检**（11-09 实测：运行 195s、各步骤成功、queue=0、未误报）。
2. **精简 cron 档位**：删 `09:35 / 10:35 / 11:35`，保留 `13:35` 与 `15:05`。理由：这三档 0% 达成、且实际落点与后三档重叠（12:00 前只有 30/667），删掉只减少无效运行，不减少有效信息。
3. **加非交易日 guard**：节假日不执行 build（历史 42 次无效运行、7 个假目录），与选项 8 合并做。

### 可选（需要决策与实测）
4. **外部定时器 PoC**：Cloudflare Worker（`services/cron-dispatch/worker.js` 已在本地待部署）+ `workflow_dispatch`，先只接 `13:35`/`15:05` 两个时点，连续 10 个交易日记录 dispatch→`run_started_at` 的真实延迟，再决定是否替换 cron。**在拿到实测数据前，不承诺任何分钟级 SLA。**
5. **checkout 瘦身**：archive 按月分目录/浅克隆，目标把 checkout 从 ~90s 降到 <20s。收益是可预期的成本下降，不是时点改善。

### 不建议
6. 通过改 cron 提前量去"对冲"延迟：延迟分布 22~741 分钟且按月漂移，固定提前量必然在部分日子落到盘中（污染收盘价）或前一日（覆盖旧数据）。
7. 自建 runner / 升配 runner：不改变运行创建时刻，无法解决本问题。
8. 为"6 档全覆盖"继续加档：在现有触发通道下，加档只会增加无效运行和假快照风险。

## 九、数据局限与未能证实的部分

1. **档位归属是推断**：GitHub API 不返回运行与 cron 的对应关系，本报告用"日内创建顺序"映射。该方法与 8 个假目录的提交时间逐一对上（§五.3），但也意味着：若某天 GitHub 丢弃了中间档位，后续档位会被前移一位。11-09 的 5 档缺失正是这种情况——该日唯一运行被映射到第 1 档（延迟 421 分钟）；若它实际是第 6 档，延迟为 91 分钟。该不确定性只影响 11-09 单日与 11 月中位的小数位，**不改变任何月度或全期结论**。
2. **`created_at` 之前不可观测**：无法区分"cron 迟到"与"GitHub 内部调度队列积压"，二者都落在运行创建之前。这也是为什么只能判定为"外部不可控"，不能给出更细的根因。
3. **无 GitHub 状态页/账户侧数据**：8 月窗口（08-07~08-26 突然变快、08-27 突然变慢）无法确认是否与平台事件相关。**不做因果归因。**
4. **账户配额无法取证**：匿名 API 读不到账单；但排队延迟恒为 0，已从行为上排除 runner 供给问题。
5. **分步耗时只抽样 10 条**（每月 1~2 条），趋势结论（checkout 变慢）有 5 个时间点支撑，但不是全量统计。
6. **11 月数据不完整**：截至 2026-11-09 17:23 CST，11 月只有 5 个完整交易日 + 11-09 的 1 次运行；11 月的中位 464 分钟会随后续运行小幅变动。
7. **本地仓库落后于远端**：本地 archive 只到 `2026-11-03`（107 个目录），archive 体积 218MB 来自本地文件系统；仓库总体积以 API `size=177553KB` 为准。
8. **`workflow_dispatch` 无历史样本**：全期 667 条运行 `event` 全部为 `schedule`，因此"外部定时器能把延迟降到多少"**无法用现有数据回答**，必须实测。
